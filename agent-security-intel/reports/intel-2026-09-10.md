### 🔍 深度分析

**是什么**：Prismor（PrismorSec，Apache-2.0，PyPI 可装）是自托管的 AI agent 运行时安全控制平面：在工具调用执行前介入，提供观察（observe）/人工审批（HITL approve）/阻断（block）三档模式，拦截秘密外泄、提示注入、供应链投毒等恶意工具调用；本地 dashboard 呈现，策略用户自定义，对 Claude Code、Codex、LangChain 等 harness 通用。

**技术机制**：① 定位在「运行时」而非静态扫描——与 SkillSpector（技能静态扫描）、mcp-triage（MCP server 审计）形成时序互补：上架前扫描、运行中裁决；② 自托管 + 本地 dashboard 意味着裁决日志与策略不出企业边界，与 SaaS 方案对比是合规卖点；③ 「agent agnostic」靠拦截工具调用抽象层实现（类似 eBPF 之于网络），策略引擎与具体 harness 解耦。

**证据强度**：早期项目（活跃度高、README 工程化程度好，提供 Skill 引导上手），但无独立安全评估/审计；控制平面自身成为高价值目标（谁能控制 Prismor 谁就能放行恶意调用）的风险未见讨论。

**四层定位与趋势判断**：纯 L2 条目，但与第 5 名 pipelock（egress 防火墙）、第 2 名 mcp-triage、第 3/4 名 AI-Infra-Guard/SkillSpector 同日聚齐——**AgentOS 运行时安全层从单品走向套件化**，这是 L2 防御工程化的收敛信号。与硬件抓手的关系：Prismor 的裁决点运行在主机 OS 层，恰是未来下沉到安全岛/TEE 的候选位置——「谁裁决 agent 的工具调用」与「裁决组件自身可信」是 L2×L3 的接口问题。

**影响与对策**：① Agent 系统建设者——灰度模式先 observe 再 enforce，避免误杀正常调用；② 防御者——把 Prismor 类控制平面的策略与审计日志纳入自己的信任边界评估（控制平面被攻陷＝全部 agent 失守）；③ 跟踪建议——观察其策略表达能力是否覆盖 A2A/多 agent 场景。
