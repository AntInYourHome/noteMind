### 🔍 深度分析

**是什么**：Containing the Autonomous Operator（arXiv v1，未经同行评审）——LLM agent 从聊天界面进入基础设施运维（读遥测/调工具/生成执行代码/修改生产 Kubernetes 状态）后的**纵深防御参考架构**。核心论点直白有力：agent 在 K8s 上操作抹掉了传统云原生安全假设的边界——**数据与控制平面之间的边界**：agent 只是一行日志、一张工单、一段工具描述就可能被改向。因此**模型不能被当作安全边界**，agent 安全是基础设施问题——一切保证必须在「agent 被提示注入完全攻陷」的假设下仍然成立。

**技术机制**：五项贡献——① 与 OWASP Agentic 对齐的十类威胁分类；② 九条设计原则，核心是**工具边界的完全中介（complete mediation）**与**切断「不可信输入×敏感访问×外部出口」的组合**；③ 七层纵深防御框架，每层映射到 K8s 原生机制（workload identity、RBAC+ValidatingAdmissionPolicy、gVisor/Kata 沙箱、FQDN 感知出口策略、agent/MCP 网关策略即代码、eBPF 运行时强制）；④ EKS/AKS/GKE 三云的具体参考架构与策略工件；⑤ 威胁-控制覆盖矩阵+四个攻击走查（定性）。

**证据强度**：单作者 v1，定性评估为主（无实测攻击成功率/开销数据——作者自己声明）。

**四层定位与趋势判断**：L2 治理层的关键论文——「假设 agent 完全被攻陷，在基础设施层做保证」与我们「假设 NS 域不可信，在硬件层做保证」**是同一原则在相邻层的独立推导**：我们下沉到 TEE/安全岛，它下沉到 K8s 原生机制（eBPF/RBAC/沙箱）。七层框架的「完全中介」=我们的强制互连；「切断不可信输入×敏感访问×出口组合」=我们的三件套。**该论文可作为方案在云原生侧的对偶参照**：K8s 层保证的是运维面，硬件层保证的是物理面，两层的交集（TEE 内跑 agent 网关）是合流点。

**影响与对策**：① 方案文档可引用该论文作为「假设下游不可信」原则的独立来源；② 其七层映射表是 K8s 落地件的现成清单；③ 关注后续实测版本（当前定性）。
