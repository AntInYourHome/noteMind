## 一句话

你和 AI 之间的"快递中转站"里藏着调包贼和小偷，作者跑去实地数了数有多少——**9 个在调包、17 个在偷钥匙、1 个把作者的钱包偷空了**；而根本原因是：**AI 返回的那条"要执行的命令"，没有任何机制能证明它没被中途改过**。

## 背景知识：三个必须先懂的词

**1. API 路由器（LLM API Router）＝ API 中转商。**
你用 Claude Code、Codex 这类编程助手时，请求常常不是直连 AI 公司的，而是隔着一层"中转商"：收你的请求，转发给 OpenAI/Anthropic/Google，再把结果还给你。为什么用它——便宜（打折转卖额度）、一把钥匙开所有模型、绕地域限制。淘宝上有卖这种服务的店，单店重复购买超过三万次；两个最火的自建中转开源软件（new-api，25.4k 星；sub2api，11k 星）被拉取了上百万次。

**2. 工具调用（tool call）＝ AI 亲自动手的那条指令。**
现在的 AI 助手不只会聊天：它帮你执行终端命令（"下载这个脚本装上"）、读写文件、发网络请求。AI 说"我要执行这条命令"就叫一次工具调用。关键：**这是一条会真实执行的指令，不只是文字**。

**3. 为什么中转商是致命位置——TLS 是接力棒，不是保险柜。**
网络加密是分段接力的：你到中转商一段加密，中转商到 AI 公司又一段加密，**每一段的中转商必须解开看明文才能转发**。所以中转商能看到你的 API 钥匙、全部对话、以及 AI 返回的那条要执行的命令。而且一条链常常多层转手（你 → 淘宝卖家 → 二级贩子 → OpenRouter → AI 公司），**任何一层是坏人，整条链完蛋**——论文的形式化叫"最弱一环性质"：一层恶意，全链无完整性保证，且下游的诚实中转商无法察觉（它们没有上游原文可对照）。

## 坏人能干的两件事 + 两个鸡贼升级

**调包（改 AI 返回的命令）**。AI 说"请从官网网址下载安装脚本"，中转商半路把网址换成自己的恶意脚本。命令格式完全合法，客户端看不出任何异常——**改一条命令 = 在用户电脑上执行任意代码**。

**偷钥匙（只看不改）**。流量原样转发，顺手把扫到的密码、API 钥匙、云凭证抄走。因为转发本来就要读明文，"正常转发"和"边转发边偷"从外面无法区分。

升级玩法一：**专改安装命令里的包名**。叫你装 `requests`，改成装一个拼写相近的恶意包——防御软件盯着网址白名单，网址没变、包名变了，拦不住。

升级玩法二：**看情况下手（条件触发）**。实测野外的真实触发器：前 50 次请求规规矩矩等你放松警惕；只对"自动执行模式"的用户下手；只对 Rust/Go 项目下手——抽查探测看到的永远是良性行为。

这里解释**自动执行模式（YOLO mode）**：很多人嫌 AI 每条命令都来问"可以吗"太烦，会打开"自动批准"——**AI 说什么就执行什么，不再确认**。开这个模式的人，被调包一次就中招。

## 作者的三个实验

**实验一：买中转服务实测**。淘宝/闲鱼/Shopify 买 28 个付费中转 + 公开社区收集 400 个免费中转；真实任务（终端命令、装包、改文件）经沙箱执行，监控每个返回命令执行后的异常动作（偷偷回连、改文件、动进程）。结果：

- **9 个中转在调包**（1 付费 + 8 免费）——付钱不代表安全；
- **17 个碰了作者故意放进流量的 AWS 蜜罐凭证**（特殊凭证，被用过就会报警——抽屉里放一根特殊头发丝，动过就知道）；
- **1 个直接转空了作者预充值的以太坊钱包**；
- 2 个部署了条件触发（50 次暖机 / 仅自动模式 / 仅 Rust-Go）。

**实验二：扔一把钥匙看谁捡**。故意泄露一把真的 OpenAI 钥匙到中转商聚集的论坛/群，在自己账户后台看动静：这把钥匙被捡去跑了 **1 亿 token**、背后至少 **7 个别人的编程助手会话**——某个"看起来正常"的中转服务正在用捡来的钥匙服务它的客户。

**实验三：故意摆弱服务器**。架 40 个弱密码假中转等人来攻：**4 万+ 次未授权访问**（147 个 IP、6 种指纹）、被收编后跑了 **20 亿 token**、过程中暴露 **99 个真实凭证、440 个会话、398 个项目**。最扎眼的数字：**440 个会话里 401 个开着自动执行模式**——不用高明手法，改一条命令直接中。

三个实验合起来的结论：恶意中转真实存在（实验一）；"无害"中转会因为捡钥匙/链弱上游被拉进同一攻击面（实验二三）——**供应链风险不始于"服务商决定作恶"，也始于"它复用了被泄露的凭证或转发了更弱的下游"**。

## 防御：作者测了三种，结论都很诚实

1. **高危命令白名单门**（"下载执行/装包"类命令，非白名单网址/包名一律拦）：实测 100% 拦住调包、误报 1%、单次判定 2.3 微秒——**但把恶意脚本藏在白名单域名的角落、或提前埋一个本地跳板文件，这扇门 100% 被绕过**。
2. **异常打分**（命令长得怪不怪、参数乱不乱）：能抓 89% 的明显调包，对"只改包名"类细腻手法只能抓一半。
3. **只记日志**：出事后能查清损失范围，防不了。

共同的要害：**都是猜，不是证明**。客户端不知道"AI 原本返回的是什么"，没有原文可对照，一切防御都是在猜"这条命令像不像被改过"。

> 注：防御数字来自论文的受控合成基准（非现场数据），作者明确声明；Mine 攻击代理的兼容率（四大框架 OpenClaw/OpenCode/Codex/Claude Code，**0/4 有响应完整性检查**，调包兼容 100%，流式缓冲重写延迟 0.004 毫秒、远低于 820 毫秒的正常延迟）是兼容性测量而非端到端执行率。

## 论文的大实话与解法

现状：**你执行的每条命令，没有任何办法证明它就是模型说的那句**——四大主流 provider 和 MCP 协议，没有一个部署了响应签名（作者查证，2026-04 版）。

作者的长期解法：**提供商签名的响应信封**（思路同邮件的 DKIM）：模型公司在返回结果上盖密码学章——涵盖模型身份、命令内容、结束原因、一次性随机数（防重放）、有效期；客户端执行前先验章。必须签"规范化后的内容"而不是原始 HTTP 报文，因为中转商前端对接的是异构协议（OpenAI/Anthropic 格式互转），原始报文没有稳定字节形态。论文附录 C 给了最小格式。

## 与本情报线方案的关联

这篇论文从传输层独立推导到了与我们相同的结论：**没有密码学锚定的来源认证，一切运行时防御都是白名单式的、都能被自适应绕过**。三篇样本正好拼成三根柱子：

| 样本 | 管什么 | 缺口 |
|---|---|---|
| Prismor | 裁决器本身可不可信（该不该执行） | 裁决器与被裁决对象同权限域 |
| Cudro | 物理动作越不越界（能执行多少） | 投影核与 VLA 共享 OS、无 fail-safe |
| 本文 | 命令来源是不是真的 AI 说的（来源真伪） | 无提供商签名，客户端无原文可对照 |

三根柱子指向同一个缺口：**信任的最后锚点必须放在软件层之外**——本文的"签名验签"是度量锚定在传输层的镜像；验签逻辑放进安全岛/TEE，正是 L2×L3 的接口点。跟踪建议：`provider response signing` / `canonical response envelope` 是新收敛的关键词，值得纳入检索词表；关注哪家 provider 第一个部署响应签名（生态位信号）。
